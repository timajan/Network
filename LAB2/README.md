# Лабораторна робота №2

## Автоматизація мережевих задач

**Тема:** Інвентаризація та перевірка контейнерної мережі засобами Python через Docker CLI та Docker Engine API.

## 1. Мета роботи

Розробити Python-застосунок для автоматизованої інвентаризації Docker-контейнерів, перевірки їхніх мережевих налаштувань та моніторингу стану контейнерної інфраструктури.

Для отримання інформації використовуються два незалежні способи:

- Docker CLI через SSH із використанням Paramiko.
- Docker Engine API через Docker SDK for Python.

Результати порівнюються та зберігаються у форматах JSON і CSV.

## 2. Архітектура

Система складається з двох машин.

### Керувальна машина

MacBook з macOS та Python 3.12.

На ньому виконуються Python-скрипти, які:

- підключаються до Ubuntu Server через SSH;
- збирають інформацію про Docker-контейнери;
- порівнюють результати CLI та API;
- перевіряють мережі й опубліковані порти;
- виконують HTTP-запити;
- формують звіти;
- здійснюють періодичний моніторинг.

### Цільова машина

Ubuntu Server 24.04 із Docker Engine та Docker Compose.

На сервері запущений Docker Compose-проєкт `university_lab1`.

Проєкт містить:

| Сервіс | Кількість | Призначення |
|---|---:|---|
| proxy | 1 | Nginx, зворотний проксі |
| app | 2 | FastAPI, обробка HTTP-запитів |
| db | 1 | Redis, зберігання лічильника запитів |

### Мережі

Використовуються дві ізольовані Docker-мережі:

**frontend — 10.240.10.0/24**

Підключені:
- proxy
- app-1
- app-2

**backend — 10.240.20.0/24**

Підключені:
- app-1
- app-2
- db

Контейнери застосунку підключені до обох мереж.

Redis доступний лише через backend-мережу.

Єдиний опублікований порт належить Nginx:

`127.0.0.1:18080:80`

Порт прив'язаний до loopback-інтерфейсу Ubuntu Server і не відкритий безпосередньо в зовнішню мережу.

## 4. Встановлення

Клонувати репозиторій та перейти до каталогу проєкту.

Створити віртуальне середовище:

```bash
python3.12 -m venv .venv
```

Активувати його:

```bash
source .venv/bin/activate
```

Встановити залежності:

```bash
python -m pip install -r requirements.txt
```

## 5. Підготовка SSH

Для роботи необхідний SSH-доступ із керувальної машини до сервера Ubuntu.

Перевірити підключення:

```bash
ssh -p <SSH_PORT> <SSH_USER>@<SSH_HOST>
```

На сервері мають бути встановлені Docker Engine і Docker Compose.

SSH-користувач повинен мати дозвіл на виконання Docker-команд.

Налаштування SSH-доступу виконується поза репозиторієм. Приватні SSH-ключі не зберігаються у проєкті.

## 6. SSH-тунель для HTTP-перевірок

Оскільки Nginx доступний лише через loopback-інтерфейс Ubuntu Server, для HTTP-перевірок використовується SSH port forwarding.

На MacBook в окремому терміналі:

```bash
ssh -N -p <SSH_PORT> \
  -L 18080:127.0.0.1:18080 \
  <SSH_USER>@<SSH_HOST>
```

Після встановлення тунелю перевірити:

```bash
curl http://127.0.0.1:18080
```

HTTP-запит через SSH-тунель надходить до Nginx, який перенаправляє його на один із двох контейнерів FastAPI.

## 7. Інвентаризація Docker

Основний скрипт:

```bash
python main.py
```

Скрипт виконує сім етапів:

1. Збір інформації через Docker CLI.
2. Збір інформації через Docker Engine API.
3. Порівняння отриманих даних.
4. Перевірка конфігурації контейнерних мереж.
5. Перевірка HTTP-доступності.
6. Формування таблиці відповідності мереж і контейнерів.
7. Перевірка опублікованих портів.

### Дані інвентаризації

Для контейнерів збираються:

- повний ідентифікатор контейнера;
- назва сервісу;
- Docker-образ;
- стан контейнера;
- час запуску;
- мережі та IP-адреси;
- опубліковані порти;
- назва хоста;
- назва Docker Compose-проєкту;
- час інвентаризації.

## 8. Порівняння Docker CLI та API

Результати, отримані через Docker CLI і Docker Engine API, нормалізуються до спільного формату.

Контейнери порівнюються за повними ідентифікаторами незалежно від порядку отримання.

Перевіряються:

- наявність контейнерів;
- назви сервісів;
- Docker-образи;
- стани;
- мережі;
- опубліковані порти.

Якщо розбіжностей немає, результат перевірки — `MATCH`.

## 9. Перевірка HTTP

Скрипт виконує два послідовні HTTP-запити до Nginx.

Для кожного запиту фіксуються:

- HTTP status code;
- час відповіді в мілісекундах;
- ідентифікатор контейнера FastAPI;
- значення лічильника Redis;
- повідомлення про помилку, якщо запит не вдався.

Перевірка вважається успішною, якщо сервер відповідає HTTP 200 і значення лічильника збільшується.

## 10. Результати роботи

Після запуску `main.py` створюються:

### inventory.json

Містить структуровану інформацію про контейнери, результати інвентаризації через CLI та API, порівняння, мережі й порти.

### report.csv

Містить підсумки автоматизованих перевірок із часовими мітками.

Приклад успішного виконання:

```text
=== SUMMARY ===
CLI/API comparison: MATCH
Network configuration: PASS
HTTP check: PASS
```

## 11. Періодичний моніторинг

Для додаткового завдання реалізований `monitor.py`.

Запуск:

```bash
python monitor.py --interval 10
```

Скрипт періодично перевіряє:

- стан контейнерів;
- Docker health status;
- HTTP-доступність;
- час HTTP-відповіді;
- помилки підключення.

Результати додаються до файлу:

`monitoring.csv`

Для завершення моніторингу використовується `Ctrl+C`.

## 12. Демонстрація відмови Redis

Для перевірки стійкості моніторингу можна тимчасово зупинити Redis-контейнер.

На Ubuntu Server:

```bash
docker stop university_lab1-db-1
```

Під час зупинки Redis моніторинг продовжує працювати та фіксує зміну стану контейнера й помилки HTTP-перевірки.

Відновлення контейнера:

```bash
docker start university_lab1-db-1
```

Після відновлення Redis HTTP-перевірки знову повертають успішні результати.

**Увага:** ці команди призначені лише для навчального Docker Compose-проєкту `university_lab1`.

## 14. Висновок

У лабораторній роботі реалізовано Python-застосунок для автоматизації інвентаризації Docker-контейнерів і перевірки їхньої мережевої конфігурації.

Використано два способи отримання даних: Docker CLI через SSH і Docker Engine API. Результати порівнюються автоматично, а перевірки мереж, портів та HTTP-доступності формуються у вигляді JSON- і CSV-звітів.

Додатково реалізовано періодичний моніторинг, який дозволяє виявляти відмови контейнерів і фіксувати їх відновлення.
